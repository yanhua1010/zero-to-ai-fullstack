# RAG 核心概念

## 什么是 RAG

RAG 是 Retrieval-Augmented Generation 的缩写,中文叫"检索增强生成",是一种把信息检索和大语言模型生成结合起来的架构。系统先把用户的问题转成向量,在向量库里找到语义最相关的文档片段,再把这些片段连同问题一起交给大语言模型来生成最终回答。它的核心目的是把外部知识注入大语言模型的上下文窗口,从而显著提升回答的准确性,并大幅减少模型幻觉。

## 为什么选 RAG 而不是微调

RAG 和微调是给 LLM 注入领域知识的两条主要路径。微调适合改变模型的行为方式或语气,但更新知识的成本高、周期长,而且新知识进不去已经训练完的参数。RAG 适合知识频繁变化的场景,因为知识库的更新只需要重新跑一次 ETL 管道,不需要碰模型本身。对于绝大多数业务问答场景,RAG 是性价比更高的选择。

## RAG 的两个阶段

RAG 系统在运行时分成两个阶段:检索阶段和生成阶段。检索阶段把用户问题转成向量,在向量库里找出语义最接近的文档片段,通常取 top-3 到 top-5 个。生成阶段把这些片段连同原始问题一起组装成 Prompt,交给大语言模型生成答案。两阶段职责清晰:检索负责把对的资料找出来,生成负责把找出来的资料组织成人能读的回答。

## Embedding 是什么

Embedding 是把一段文本映射成一个高维向量的过程,典型维度是 1536 维(对应 OpenAI 的 text-embedding-3-small)。这个向量编码了文本的语义信息——意思相近的文本,生成的向量在高维空间里的距离也近。RAG 系统就是靠 embedding 实现"语义检索":不是按关键词匹配,而是按语义相似度找最近邻。

## 向量数据库的角色

向量数据库专门用来存储和查询高维向量,典型代表是 pgvector(PostgreSQL 扩展)、Chroma、Pinecone、Milvus。在 RAG 里,向量数据库负责存放所有文档分块对应的 embedding 向量,并通过近似最近邻搜索(ANN)在毫秒级内返回与查询向量最接近的若干个分块。pgvector 提供三种距离算子:`<=>` 余弦距离最适合 RAG 场景,`<->` 是欧式距离,`<#>` 是负内积。

## 为什么要标注来源

RAG 系统的回答必须标注来源,理由有两条。第一是让用户能核实答案是否可信——没有出处的 AI 回答和直接问模型没有本质区别。第二是当模型答错时能快速定位到底是哪段文档误导了它,这是日常调优最重要的入口。生产 RAG 系统如果不带来源标注,基本就失去了"可信"和"可调"两个最大的优势。

## 检索质量决定回答上限

RAG 的回答质量上限完全由检索质量决定。如果检索阶段没有把相关文档找出来,生成阶段再强的模型也只能基于错误或缺失的上下文作答,最多答得通顺,但内容不准。所以调优 RAG 时应该先确认检索召回是否准确,再去优化 Prompt 或换更强的生成模型。把精力花在调 Prompt 上而忽视检索,是最常见的错误优化方向。

## 多轮对话中的指代问题

在多轮对话里,用户经常用"它""这个""那家公司"这类代词指代前文。RAG 链需要把对话历史一起带给生成模型,模型才能理解这些代词到底指什么,进而决定这一轮该检索什么。一个常见的工程做法是用 LLM 先做"问题重写"——把用户当前的问题和历史一起送进模型,让模型输出一个独立、不含代词的新问题,再拿这个新问题去做向量检索,这样检索质量会显著提高。
